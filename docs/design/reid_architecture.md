# Re-ID アーキテクチャ設計

- 最終更新: 2026-11-01
- 対象: `filter.py`（`process_frame`）、`reid.py`、`id_manager.py`、`zone_analytics.py`

## この文書の目的

ByteTrack と OSNet の責務分担、および `track_id` と `real_id` の扱いを定める。
「何を実現したいか」（ブース別の来場者数と滞在時間の計測）は要件であり、本文書では扱わない。
本文書は「どう実現するか」を定める。

現状のコードと、目指す形の両方を記載し、その差分を一覧にする。
差分が解消されたらその行を削除し、現状の記述に統合する。

## 1. 責務分担

### 基本方針

ByteTrack と OSNet は使える情報が異なる。それぞれが得意な領域に限定して使う。

| 担当 | 使う情報 | 得意な場面 | 使えない場面 |
|---|---|---|---|
| ByteTrack | 位置と動きの連続性 | 画面内で映り続けている人の追跡 | 画面外に出た後、追跡が切れた後 |
| OSNet | 外見の特徴 | 時間的に離れた画像どうしの照合 | 似た外見の別人の区別 |

**判断の基準は「画面外かどうか」ではなく「`track_id` が切れたかどうか」とする。**
画面外への退出と、遮蔽で ByteTrack が別 ID を振った場合は、
どちらも「同一人物だが `track_id` が異なる」という同じ構造の問題である。
区別する処理を設けると条件分岐が増えるため、区別しない方が単純になる。

### 救済手段の対応

| 状況 | `track_id` | 救済手段 |
|---|---|---|
| 画面内で追跡継続 | 継続 | 不要 |
| 短時間の検出漏れ、同じ ID で復活 | 継続 | `buffer_time`（3秒） |
| 遮蔽明けに別 ID で復活 | 切断 | **OSNet** |
| 画面外に出て戻る | 切断 | **OSNet** |

`buffer_time` は `ZoneAnalytics` が持つ仕組みで、`track_id` が同一の場合にしか働かない。
役割としては ByteTrack 側の補強にあたる。

## 2. ID の種類

| ID | 発生元 | 形式 | 変わるタイミング | 寿命 |
|---|---|---|---|---|
| `track_id` | ByteTrack | 整数 | 追跡が切れると新しい値 | 画面内にいる間 |
| `real_id` | `IDManager` | `R001` / `S001` | 待機明けの最初の照合時のみ。スタッフ登録時はスタッフ ID に置き換わる | セッション中（`timeout_seconds = 1800`） |

`real_id` は `track_to_real_id`（`track_id` をキーとする辞書）で管理する。
新しい `track_id` が現れるたびに仮の `real_id` を発行し、
待機明けの最初の照合で既存の人物と一致した場合にのみ、その `real_id` で上書きする。
照合が済んだトラック（`confirmed_tracks`）は、追跡が続く間は再照合しない。

スタッフ登録（`register_staff(feature, track_id)`）では、登録したトラックの `real_id` を新しいスタッフ ID に置き換える。

そのため、**照合で既存 ID に置き換わった場合、発行した番号は欠番になる。**
`next_real_id` の値は実際の来場者数より大きくなる。

## 3. 特徴量プールの設計

### 方針

1人につき複数の特徴量を保持する。**同一人物でありながら向きが異なり、
かつ類似度が極端に近くない画像**を蓄積する場所として設計する。
角度や照明が変わっても照合できるようにするためである。

| パラメータ | 値 | 意味 |
|---|---|---|
| `MAX_POOL_SIZE` | 5 | 1人あたりの保持枚数 |
| `diversity_threshold` | 0.90 | これ以上似ている場合はプールに追加しない |
| `similarity_threshold` | 0.70 | これ以上なら同一人物と判定 |
| `POOL_UPDATE_INTERVAL` | 15 | 照合後、プールへの追加を試みる間隔（フレーム） |

照合はプール内の全特徴量と総当たりし、最高スコアを採用する。
プールが多様な姿を持つ以上、全件と比較する必要がある。

### プールへの追加のタイミング

| タイミング | 条件 |
|---|---|
| 照合時（既存の人物と一致） | 一致スコアが 0.90 未満なら追加 |
| 照合時（誰とも一致しない） | 新しい来客プール `[feature]` を作成 |
| 追跡継続中 | `POOL_UPDATE_INTERVAL` ごとに特徴を抽出し、**自分のプール**との最高スコアが 0.70 以上 0.90 未満なら追加。0.70 未満は ID スイッチを疑い追加しない |
| スタッフ登録時 | インデックス0に登録時の特徴量を置き、登録したトラックの来客プールから最大4枚を引き継ぐ（来客プールは削除） |

### スタッフと来客で削除位置を変える理由

| 対象 | 削除位置 | 理由 |
|---|---|---|
| スタッフ | `pop(1)` | **インデックス0（登録時の特徴量）を保護する。** 登録時は正面・全身・単独で撮影するため、理想的な特徴量が得られる。これを捨てるべきではない |
| 来客 | `pop(0)` | 来客はどの角度で映るか事前に決められず、保護すべき「正解」が存在しない。完全な FIFO とする |

この使い分けは意図的なものであり、不具合ではない。

## 4. 現状の処理フロー

```
process_frame（毎フレーム）
  ├─ YOLO + ByteTrack（model.track, conf=0.1, classes=[0], persist=True, bytetrack.yaml）
  │    └─ 追跡開始・第1段は 0.6、第2段（低スコア検出での追跡継続）は 0.1
  └─ 検出された人ごとに繰り返し
       ├─ 検出枠そのままで切り出し（全身）
       ├─ id_manager.resolve(track_id, crop_img, live_track_ids)
       │    ├─ 期限切れセッションの掃除（30分見えない来客はアーカイブ）
       │    ├─ track_id が新規なら real_id を仮発行
       │    ├─ track_age < WAIT_FRAMES(5) なら "waiting" で即return（特徴抽出なし）
       │    ├─ 照合済みのトラック → 照合せず、POOL_UPDATE_INTERVAL ごとにプール追加のみ
       │    └─ 未照合のトラック（特徴抽出に失敗したら "Unknown" で次フレームに再試行）
       │         ├─ 画面内の他トラックが持つ real_id を候補から除外
       │         ├─ スタッフ・来客の両方と総当たりし、高い方を採用（argmax）
       │         │    ├─ 0.70以上でスタッフが上 → "staff"
       │         │    ├─ 0.70以上で来客が上   → "matched_visitor"
       │         │    └─ どちらも未満        → "new_visitor"、新規プール作成
       │         └─ confirmed_tracks に登録
       └─ raw_tracks に詰める
  ↓
zone_analytics.update(raw_tracks, ...)
  ├─ 滞在を real_id 単位で管理（waiting / Unknown は計測しない）
  ├─ ブース移動・ブース外への移動で退場を記録
  └─ 見失った real_id は buffer_time(3秒) 待って確定。滞在は見失った時点まで
       （3秒以内に別トラックで戻れば同じ滞在として継続）
```

### スタッフ登録の流れ

```
登録操作（server.py の登録ボタン / camtest.py の s キー）
  └─ register_largest_as_staff(img, results)
       ├─ process_frame の追跡結果から最大の人物を選ぶ（track_id が分かる）
       └─ id_manager.register_staff(feature, track_id)
            ├─ 採番は既存スタッフ番号の最大値 + 1
            ├─ そのトラックの来客プールを引き継ぎ、来客辞書から削除
            └─ トラックをスタッフとして照合済みにする
```

### status の種類

| status | 意味 | reid_score |
|---|---|---|
| `waiting` | `WAIT_FRAMES` 未満。判定を保留中 | 0.0 |
| `Unknown` | 特徴抽出に失敗。次フレームで再試行 | 0.0 |
| `staff` | スタッフと一致 | 照合時の最高スコア（登録で確定した場合は 1.0） |
| `matched_visitor` | 来客と一致 | 照合時の最高スコア |
| `new_visitor` | 誰とも一致せず、新規登録 | 照合時の最高スコア（閾値未満の値） |

## 5. 処理フローの方針

2026-11-01 に実装済み（§4）。方針とその理由を残す。

```
新しい track_id が出現したとき
  → OSNet で照合し、real_id を決定する
  → 一致すれば、その real_id の滞在を継続させる

track_id が継続している間
  → OSNet による照合は行わない（ByteTrack の判断を信頼する）
  → 滞在時間は real_id を単位として連結する
```

`track_id` が継続している間は、ByteTrack が位置の連続性という強い根拠を持っている。
その状態で OSNet が毎フレーム判定を上書きできる構造は、判断が揺れる原因になる。

## 7. 既知の制約

### 最初の照合の誤りが追跡中に修正されない

照合は1トラックにつき1回のため、最初に別人と判定すると、追跡が続く間はその `real_id` のままになる。
さらに、照合時と追跡中のプール追加で、誤った相手のプールに特徴量が入る。
追跡中の追加は自分のプールと 0.70 以上の場合に限るため、汚染は照合時の1枚に限られやすいが、検出はしていない。

### 登録前の滞在は来客として記録される

カメラの前で登録したスタッフは、登録前に来客として照合されている。
登録した時点でその来客の滞在は見失い扱いになり、来客の行として記録される（1秒未満なら記録されない）。
開場前に登録する運用であれば影響はない。

## 8. 未決事項

結論が出ていない項目を記す。決まり次第、該当する節へ移す。

### プール追加の効果（実装済み・未検証）

照合と分離したプール追加（§3「プールへの追加のタイミング」）を実装した。
`POOL_UPDATE_INTERVAL = 15` と、追加の下限 0.70 は暫定値である。
蓄積された姿が再入場時の照合率を上げているか、汚染を増やしていないかは未検証。

### 上位スコアが僅差の場合の判定

`_find_best_match` は最高スコアのみを返し、2位との差を見ていない。
2026-10-01 の実験では、1439 の本人ペアが 0.9053〜0.9498、
別人（0295）とのペアが最高 0.8935 であり、**上位が僅差になる事例が実在する。**

1位と2位の差が小さい場合に判定を保留する方式が有効かどうかは未検証である。
既存の実験 CSV から、僅差がどの程度の頻度で起きるかを確認できる。

### ByteTrack の遮蔽耐性と OSNet の照合性能の比較

遮蔽時に OSNet を使うべきかは、ByteTrack がどこまで遮蔽に耐えるかによる。
両者を比較していないため、どの条件が最良かは不明である。

比較には動画データが必要であり、Market-1501 のような静止画では測れない。
DukeMTMC-VideoReID、MARS、または実際の会場映像が候補となる。

評価指標は類似度ではなく、**1人の滞在が何本の記録に分割されたか**とする。
理想は1人1本である。

### 入力画像の切り出し方

2026-09-10 の検証で、全身画像よりバストアップの方がスコアが高い傾向が確認されている。
現状は検出枠そのままの全身である。変更すべきかは未検証。

### 来客プールの汚染検出

誤マッチが起きると別人の特徴量がプールに混入し、
来客は `pop(0)` のため本人の姿から先に失われる。
汚染が実際に起きているか、起きた場合に検出できるかは未検討である。

### 適合率と再現率のどちらを優先するか

本システムはカメラ1台で会場全体を覆えないため、
来場者が画面外に出て戻る頻度が高い。
見失いは出入りのたびに発生するため、**再現率を優先すべきと考えている。**

ただし蓄積人数が増えると照合相手のほぼ全員が別人になるため、適合率は低下する。
再現率を優先しつつ適合率の下限を設ける運用が必要と考えられるが、
その下限値は未決である。
