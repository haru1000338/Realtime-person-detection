# Re-ID アーキテクチャ設計

- 最終更新: 2026-10-01
- 対象: `main.py`（`process_frame`）、`reid.py`、`id_manager.py`、`zone_analytics.py`

## この文書の目的

ByteTrack と OSNet の責務分担、および `track_id` と `real_id` の扱いを定める。
「何を実現したいか」（ブース別の来場者数と滞在時間の計測）は要件であり、本文書では扱わない。
本文書は「どう実現するか」を定める。

現状のコードと、目指す形の両方を記載し、その差分を一覧にする。
差分が解消されたらその行を削除し、現状の記述に統合する。

## 1. 責務分担

### 基本方針

ByteTrack と OSNet は使える情報が異なる。それぞれが得意な領域に限定して使う。

| 担当 | 使う情報 | 得意な場面 | 使えない場面 |
|---|---|---|---|
| ByteTrack | 位置と動きの連続性 | 画面内で映り続けている人の追跡 | 画面外に出た後、追跡が切れた後 |
| OSNet | 外見の特徴 | 時間的に離れた画像どうしの照合 | 似た外見の別人の区別 |

**判断の基準は「画面外かどうか」ではなく「`track_id` が切れたかどうか」とする。**
画面外への退出と、遮蔽で ByteTrack が別 ID を振った場合は、
どちらも「同一人物だが `track_id` が異なる」という同じ構造の問題である。
区別する処理を設けると条件分岐が増えるため、区別しない方が単純になる。

### 救済手段の対応

| 状況 | `track_id` | 救済手段 |
|---|---|---|
| 画面内で追跡継続 | 継続 | 不要 |
| 短時間の検出漏れ、同じ ID で復活 | 継続 | `buffer_time`（3秒） |
| 遮蔽明けに別 ID で復活 | 切断 | **OSNet** |
| 画面外に出て戻る | 切断 | **OSNet** |

`buffer_time` は `ZoneAnalytics` が持つ仕組みで、`track_id` が同一の場合にしか働かない。
役割としては ByteTrack 側の補強にあたる。

## 2. ID の種類

| ID | 発生元 | 形式 | 変わるタイミング | 寿命 |
|---|---|---|---|---|
| `track_id` | ByteTrack | 整数 | 追跡が切れると新しい値 | 画面内にいる間 |
| `real_id` | `IDManager` | `R001` / `S001` | 照合で既存 ID に置き換わる | セッション中（`timeout_seconds = 1800`） |

`real_id` は `track_to_real_id`（`track_id` をキーとする辞書）で管理する。
新しい `track_id` が現れるたびに仮の `real_id` を発行し、
OSNet の照合が成功した場合にのみ既存の `real_id` で上書きする。

そのため、**照合で既存 ID に置き換わった場合、発行した番号は欠番になる。**
`next_real_id` の値は実際の来場者数より大きくなる。

## 3. 特徴量プールの設計

### 方針

1人につき複数の特徴量を保持する。**同一人物でありながら向きが異なり、
かつ類似度が極端に近くない画像**を蓄積する場所として設計する。
角度や照明が変わっても照合できるようにするためである。

| パラメータ | 値 | 意味 |
|---|---|---|
| `MAX_POOL_SIZE` | 5 | 1人あたりの保持枚数 |
| `diversity_threshold` | 0.90 | これ以上似ている場合はプールに追加しない |
| `similarity_threshold` | 0.70 | これを超えたら同一人物と判定 |

照合はプール内の全特徴量と総当たりし、最高スコアを採用する。
プールが多様な姿を持つ以上、全件と比較する必要がある。

### スタッフと来客で削除位置を変える理由

| 対象 | 削除位置 | 理由 |
|---|---|---|
| スタッフ | `pop(1)` | **インデックス0（登録時の特徴量）を保護する。** 登録時は正面・全身・単独で撮影するため、理想的な特徴量が得られる。これを捨てるべきではない |
| 来客 | `pop(0)` | 来客はどの角度で映るか事前に決められず、保護すべき「正解」が存在しない。完全な FIFO とする |

この使い分けは意図的なものであり、不具合ではない。

## 4. 現状の処理フロー

```
process_frame（毎フレーム）
  ├─ YOLO + ByteTrack（model.track, persist=True, bytetrack.yaml）
  └─ 検出された人ごとに繰り返し
       ├─ 検出枠そのままで切り出し（全身）
       ├─ id_manager.resolve(track_id, crop_img)
       │    ├─ 期限切れセッションの掃除
       │    ├─ track_id が新規なら real_id を仮発行
       │    ├─ track_age < WAIT_FRAMES(5) なら "waiting" で即return（特徴抽出なし）
       │    ├─ 特徴抽出（OSNet）
       │    ├─ スタッフ辞書と総当たり → 0.70以上で "staff" に昇格、プール更新
       │    └─ 来客辞書と総当たり
       │         ├─ 0.70以上 → その real_id を採用、プール更新
       │         └─ 未満 → "new_visitor"、新規プール作成
       └─ raw_tracks に詰める
  ↓
zone_analytics.update(raw_tracks, ...)
  └─ 滞在時間を track_id ベースで管理。real_id は記録に添えるのみ
```

### status の種類

| status | 意味 | reid_score |
|---|---|---|
| `waiting` | `WAIT_FRAMES` 未満。判定を保留中 | 0.0 |
| `staff` | スタッフ辞書と一致 | 0.0 |
| `matched:0.85` | 来客辞書と一致。数値は類似度 | 実値 |
| `new_visitor` | 誰とも一致せず、新規登録 | 0.0 |
| `Unknown` | 特徴抽出に失敗 | 0.0 |

**一致しなかった場合に類似度が記録されない。**
「最も似ていた相手が 0.65 で閾値に届かなかった」という情報が 0.0 として残るため、
本番ログから閾値の妥当性を検証できない。

## 5. 目指す処理フロー

現状との違いは2点である。

```
新しい track_id が出現したとき
  → OSNet で照合し、real_id を決定する
  → 一致すれば、その real_id の滞在を継続させる

track_id が継続している間
  → OSNet による照合は行わない（ByteTrack の判断を信頼する）
  → 滞在時間は real_id を単位として連結する
```

`track_id` が継続している間は、ByteTrack が位置の連続性という強い根拠を持っている。
その状態で OSNet が毎フレーム判定を上書きできる構造は、判断が揺れる原因になる。

## 6. 現状との差分

| # | 項目 | 目指す形 | 現状 | 優先度 |
|---|---|---|---|---|
| 1 | 重み | Re-ID 学習済み（`osnet_x1_0_msmt17.pth` 等） | **ImageNet 分類用**（`model_path` 未指定） | 高 |
| 2 | 滞在の連結 | `real_id` を単位とする | `track_id` のみ。`real_id` は記録に添えるだけ | 高 |
| 3 | 照合のタイミング | 新しい `track_id` の出現時のみ | 検出された全員、毎フレーム | 中 |
| 4 | 照合の相手 | 画面にいない人のみ | `active_visitors` 全員（画面内の人も含む） | 中 |
| 5 | 入力画像 | 要検討（9月の検証でバストアップ優位） | 検出枠そのまま（全身） | 中 |
| 6 | 不一致時のログ | 最高スコアを記録する | 0.0 として記録される | 低 |

### 補足

**#1** は `FeatureExtractor` に `model_path` を渡すのみで修正できる。
これを行わない限り、他の改善を検証しても結果を解釈できない。

**#2** が未実装であるため、現状は **Re-ID の判定結果が集計に反映されていない。**
OSNet を導入している意味が実質的にない状態である。

**#3** と **#4** は関連する。照合を新しい `track_id` の出現時に限定すれば、
画面内にいる人を相手にする必要もなくなる。
ただし #3 を単純に実装すると、追跡継続中にプールが更新されなくなるため、
「照合」と「プールへの追加」を分離する必要がある（未決事項を参照）。

## 7. 既知の不具合

### `_clean_expired_sessions` のアーカイブ処理が実行されない

```python
for real_id, last_time in self.last_seen.items():
    if real_id in self.active_visitors:
        continue                      # active なものは expired_ids に入らない
    ...
for real_id, last_time in expired_ids:
    if real_id in self.active_visitors:   # ここに来る時点で必ず False
        self.archived_visitors[real_id] = self.active_visitors.pop(real_id)
```

1つ目のループで `active_visitors` にある ID を除外しているため、
2つ目のループの条件は常に成立しない。**アーカイブ処理は一度も実行されない。**

結果として `active_visitors` はセッション中に増え続ける。
照合相手が増えるほど誤マッチの機会が増え、総当たり比較の回数も増加する。

### `reid.py` のコメントと実装が一致していない

```python
# RTX 5060 TiのCUDA対応待ちのため、安定動作するCPUモードを強制指定
device = 'cuda' if torch.cuda.is_available() else 'cpu'
```

コメントは CPU 固定と記載しているが、実装は CUDA を優先する。

## 8. 未決事項

結論が出ていない項目を記す。決まり次第、該当する節へ移す。

### 照合とプール更新を分離するか

差分 #3 を実装すると、追跡継続中に OSNet を呼ばなくなるため、
プールに新しい姿が蓄積されなくなる。

案として、次の分離が考えられる。

| 処理 | タイミング | 目的 |
|---|---|---|
| 照合（`real_id` の決定） | 新しい `track_id` の出現時のみ | 人物の特定 |
| プールへの追加 | 追跡継続中、一定間隔で | 多様な姿の蓄積 |

追跡継続中は `real_id` が確定しているため、照合せずに追加のみ行える。
ただし未検証である。

### 上位スコアが僅差の場合の判定

`_find_best_match` は最高スコアのみを返し、2位との差を見ていない。
2026-10-01 の実験では、1439 の本人ペアが 0.9053〜0.9498、
別人（0295）とのペアが最高 0.8935 であり、**上位が僅差になる事例が実在する。**

1位と2位の差が小さい場合に判定を保留する方式が有効かどうかは未検証である。
既存の実験 CSV から、僅差がどの程度の頻度で起きるかを確認できる。

### ByteTrack の遮蔽耐性と OSNet の照合性能の比較

遮蔽時に OSNet を使うべきかは、ByteTrack がどこまで遮蔽に耐えるかによる。
両者を比較していないため、どの条件が最良かは不明である。

比較には動画データが必要であり、Market-1501 のような静止画では測れない。
DukeMTMC-VideoReID、MARS、または実際の会場映像が候補となる。

評価指標は類似度ではなく、**1人の滞在が何本の記録に分割されたか**とする。
理想は1人1本である。

### 入力画像の切り出し方

2026-09-10 の検証で、全身画像よりバストアップの方がスコアが高い傾向が確認されている。
現状は検出枠そのままの全身である。変更すべきかは未検証。

### 来客プールの汚染検出

誤マッチが起きると別人の特徴量がプールに混入し、
来客は `pop(0)` のため本人の姿から先に失われる。
汚染が実際に起きているか、起きた場合に検出できるかは未検討である。

### 適合率と再現率のどちらを優先するか

本システムはカメラ1台で会場全体を覆えないため、
来場者が画面外に出て戻る頻度が高い。
見失いは出入りのたびに発生するため、**再現率を優先すべきと考えている。**

ただし蓄積人数が増えると照合相手のほぼ全員が別人になるため、適合率は低下する。
再現率を優先しつつ適合率の下限を設ける運用が必要と考えられるが、
その下限値は未決である。
